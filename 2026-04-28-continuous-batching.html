当批次自己重组：
Continuous Batching

为什么把"按批次推理"换成"按 token 重排"，能让 LLM 推理吞吐翻 3 倍——而你只需要改调度器。

I.气泡问题 II.从 batch-step 到 token-step III.调度器实验台 IV.一次粗略估算 V.记住三件事
I.

请求并不会同时结束，可 GPU 等得起吗

生产环境里的 LLM 推理服务每天接到的 prompt 长短不一、生成长度更不一。一个简单的 chat 回复可能 30 个 token 就停了；一段代码生成可能要 800 个 token 才输出完整。 传统的静态批处理 (static batching)把 N 个请求凑成一个 batch，丢进 forward，等所有请求都生成完才开始下一批。

问题就出在"等所有请求都生成完"这一句。GPU 在 decode 阶段是memory-bound的——也就是说， 跑 1 个 sequence 和跑 8 个 sequence 的 forward 时间几乎一样，只要 KV Cache 装得下。 所以一旦 batch 里某个请求提前结束，它在剩余的 forward step 里就只是"占着 batch slot 但什么都不算"—— 整个 batch 必须凑齐到最长那个请求的长度，才能腾出位置接新请求。

Insight 静态批处理的吞吐瓶颈不是显存，也不是算力，而是请求长度的方差。 方差越大，GPU 上"空着但走不掉"的 slot 越多，这些就是batching bubbles。
II.

从 batch-step 调度，改成 token-step 调度

Continuous batching（也叫 in-flight batching、iteration-level scheduling）的核心改动其实只有一行： 调度的最小单位从"一整个 batch 跑完"换成"一个 forward step 之后"。 每完成一个 decode step（即每生成一个 token），调度器就检查： 谁结束了？把它的 KV Cache 释放掉，立刻从队列里拉一个新请求填进 batch。

Insight 连续批处理没有改变模型，没有改变 kernel，没有改变 KV Cache 的结构。 它只把"什么时候允许新请求进来"这个决定的粒度，从 batch 级别下沉到了 iteration 级别。

观察建议

把 方差 = 0、batch = 8，两种调度器吞吐差不多。 把方差拉到 0.9，static 的利用率会掉到 40% 以下，而 continuous 几乎纹丝不动。 再把 batch 加到 16，continuous 进一步逼近 100%——这就是 vLLM 那种"先把 batch 拉到 256"的现实理由。

IV.

一次粗略估算：Llama-3-70B 服务一个混合 workload

把数字带回来。假设一台 8×H100 跑 Llama-3-70B（TP=8），decode 阶段单步前向需要 ~25 ms。 接到的请求里，有人想 30 个 token（短问答），有人想 800 个 token（代码生成），平均 220 token、标准差 280 token。 batch 容量是 16。

单 decode step25 ms
最长请求长度（约 P99）~900 tokens
平均请求长度220 tokens
— Static —
batch 寿命（被最长那个拖着）900 × 25ms ≈ 22.5 s
该 batch 实际生成 tokens16 × 220 ≈ 3,520
slot 利用率 = 220 / 900≈ 24%
吞吐3,520 / 22.5 ≈ 156 tok/s基线
— Continuous —
每 step 平均活跃 slot（理想）≈ 16
slot 利用率≈ 95%
吞吐16 × 0.95 / 0.025 ≈ 608 tok/s×3.9

这就是为什么 2023 年之后没有任何主流推理引擎再用静态批处理—— vLLM、TGI、TensorRT-LLM、SGLang 全部默认开启 continuous batching。 在生成长度方差大的真实流量上，提升 3–10× 是常态。

Insight 静态批处理的吞吐被 P99 长度绑架；连续批处理的吞吐被平均长度（和 batch 容量）支配。 把吞吐瓶颈从 P99 换成平均，是 LLM 推理工程里最便宜的一次免费午餐。
V.

记住三件事

  1. Bubble 是方差造成的，不是显存或算力。 如果你的请求生成长度都接近，static 和 continuous 没区别—— 但 LLM 应用层流量天然方差大，所以这个优化几乎对所有真实 workload 都赚。
  2. Continuous batching 改的是调度，不是 kernel。 前向算子、KV Cache 布局都不动，只是把"什么时候允许新请求加入 batch"从 batch 边界改到 iteration 边界。 这也意味着它和 PagedAttention、speculative decoding、chunked prefill 互相正交，可以叠加。
  3. Continuous batching 让吞吐对 batch 容量更敏感。 在 static 下，调大 batch 没用——bubble 也跟着放大；在 continuous 下，调大 batch 几乎线性提升吞吐， 直到撞上 KV Cache 显存上限。这就是接下来要面对的问题——KV Cache 怎么管，正是 PagedAttention 要解决的事。
