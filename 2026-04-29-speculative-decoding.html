投机解码：一次猜多步，验一把

Speculative Decoding 让一个小模型替大模型先“起草”几枚 token，大模型再用一次前向把它们全部审一遍。在 memory-bound 的 decode 阶段，这种“批量赌博”常常能换来 2–3× 的加速。

I.

Decode 是 memory-bound 的，单步算力被白白浪费

大模型推理分两段：Prefill 把整段 prompt 一次性灌入，FLOPs 直接拉满；Decode 则一步生成一个 token，每生成一个新 token 都要把 KV cache、所有权重再过一遍 HBM。换句话说，decode 阶段的瓶颈不是算力，而是把权重从显存搬进 SM 的带宽。

这就埋下一颗很大的彩蛋：既然 decode 一步搬一次权重几乎等于搬十次的代价，那能不能让一次搬运顺便算十个 token？答案是：能 — 只要这十个 token 你提前猜对。

Fig. 1每根条形是一次 decode 步：HBM 搬权重的时间远大于矩阵计算的时间。compute 单元在大半时间里是空闲的——这正是“可以顺手再算几个 token”的空间。
核心直觉. 在 memory-bound 区，把 batch 从 1 变成 γ 几乎免费——只要 KV cache 装得下、SM 也算得过来。
II.

起草模型抢答，目标模型一笔验稿

投机解码引入一个小模型 Md（draft，比如 Llama-3-8B）和一个大模型 Mt（target，比如 Llama-3-70B）。流程是：

① Md 顺序生成 γ 个 draft token（很快，因为它小）。② Mt 把这 γ 个 token 一次前向跑完，拿到每个位置的真实分布。③ 从前往后比对，用修正过的拒绝采样判定接受还是拒绝。④ 第一次拒绝时，从修正分布里重采一个新 token；如果 γ 个全部接受，再白送一个。

关键设计：Mt 的那一次前向是并行的，γ 个 token 跑出来花的时间≈一次普通 decode（因为 decode 阶段它本来就在浪费算力）。所以代价表大致是 γ × T_d + 1 × T_t，产出却是 1 到 γ+1 个新 token。

Fig. 2上轨：纯 autoregressive，每个 token 一格 Tt。下轨：投机解码，γ 个细格是 draft（Td ≪ Tt），紧接着一格粗的是 target verify。绿色 = 接受，红色 = 拒绝（剩余 draft 全部丢弃）。
关键观察. 拒绝并不浪费 verify——verify 那一步本身已经给出一个新 token。真正浪费的是已经被起草、却被拒绝后的位置——所以 γ 不能取得太大。
III.

期望接受 token 数：α 与 γ 的拉锯

把每个 draft token 被接受的概率记作 α（独立同分布是个简化假设，但抓住了主要项）。设 γ 为一次起草的长度，c = Td / Tt 为草稿/目标的每步耗时比。一轮投机解码在期望意义上：

期望产出 token 数 E[N] = (1 − α^(γ+1)) / (1 − α) 一轮耗时 E[t] = γ · c + 1 （以 T_t 为单位） 期望加速比 S(α, γ) = E[N] / E[t]

α 越高、γ 越长，第一项就越接近 γ + 1（“几乎全部接受”）。但 γ 越长，分母里 γ·c 也线性涨——一旦草稿成本压过被多接受的好处，加速就掉头向下。下面这两根滑杆让你亲手把这条曲线推出来：

结论. α 决定能不能值，c 决定γ 能拉多长。生产里常见的 α ≈ 0.7、c ≈ 0.1 给出 γ* ≈ 5–7、S ≈ 2.4×。
IV.

背一遍：Llama-3-70B + 8B 的算盘

用现实数字喂这个公式。Target 取 Llama-3-70B（70B 参数，bf16 ≈ 140 GB 权重），draft 取同家族的 Llama-3-8B（≈ 16 GB）。Decode 阶段两者都被 HBM 带宽 (~3.35 TB/s on H100) 支配。粗算每 token 时间正比于权重大小 / 带宽：

量记号取值
Target 每 decode stepT_t≈ 42 ms
Draft 每 decode stepT_d≈ 5 ms
耗时比c = T_d / T_t≈ 0.12
同家族对齐 → 接受率（实测）α≈ 0.75
起草长度γ5
期望接受 (1−α^(γ+1))/(1−α)E[N]≈ 3.22 tok
期望耗时 γ·c + 1E[t]≈ 1.60 ×T_t
实际吞吐加速S≈ 2.0×

对比一下，普通 decode 一轮花 1·Tt 出 1 个 token，吞吐 1/Tt；投机解码一轮花 1.60·Tt 出 3.22 个 token，吞吐 2.01/Tt——这就是 H100 上一台 70B 服务用 8B 起草能拿到的真实提升量级。生产里再叠加 prompt-cache、tree-attention（一次起草成多条候选树），上限可以再往上推到 3×。

注意. 这一切的前提是 target 的 verify 步本来就 memory-bound——也就是 batch 还没把 GPU 算力打满。一旦做了大批量 continuous batching，verify 已经接近 compute-bound，γ 个 token 的 verify 不再“免费”，投机解码的红利会被压缩甚至消失。
V.

要记住的

投机解码不省 FLOPs，它换的是被浪费的 FLOPs。decode 阶段 GPU 算力闲置，所以 verify γ 个 token 的代价≈1 个，这才是它能赚的本质。

两个旋钮——α（接受率）和 c（起草成本比）——决定了最佳 γ*。α 高就敢押大 γ；c 高就被迫缩短 γ。

同家族对齐的 draft（蒸馏 / EAGLE / Medusa）能把 α 从 ~0.5 推到 ~0.8，是工程上最大的杠杆，比调 γ 更值得花力气。

大 batch + continuous batching 会吃掉投机解码的红利。低延迟单流场景下它收益最大；高吞吐多流场景下要谨慎评估，甚至可能亏。

生产实现里要看 tree-style speculation（一次起草多分支）和 self-speculation（target 自己当 draft，如 Medusa），它们的本质都还是 § III 的那条公式——只是 α 和 c 的取值变了。
