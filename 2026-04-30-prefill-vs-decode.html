推理时间的两副面孔 ——
Prefill 与 Decode 的不对称

同一次请求里，模型先做一段并行的"读题"，再做一段串行的"逐字回答"。这两段几乎不像同一个程序：一段被 GPU 算力卡住，一段被显存带宽卡住。理解它们的差别，是读懂 TTFT、TPOT、批处理与 KV Cache 的起点。

I.

同一次请求里，藏着两段完全不同的时间

TTFT  ≠  TPOT × N

当用户按下回车，LLM 推理服务把这次请求切成两段。第一段叫 Prefill：模型一次性吃下整个 prompt，把每一层的 K、V 都算出来，写进 KV Cache。第二段叫 Decode：模型一次只吐一个 token，每吐一个就读一遍前面所有 token 的 K/V、写一份新的 K/V 进缓存，循环到 EOS。

用户体感的两个时间，分别对应这两段：

TTFT — Time To First Token
≈ Prefill 时长
TPOT — Time Per Output Token
≈ 单步 Decode 时长

为什么把这两段放在一起讲？因为 Prefill 是 compute-bound（算力卡住），Decode 是 memory-bound（带宽卡住）。同一段 GPU、同一份权重，但瓶颈在硬件的两端。任何想优化 LLM 推理的工程决策——continuous batching、PagedAttention、speculative decoding、chunked prefill——都建立在"承认这两段不一样"这条公理上。

核心观察 Prefill 是一次"宽矩阵乘法"，吃 FLOPS。Decode 是一连串"瘦矩阵乘 + 读 KV Cache"，吃 HBM 带宽。把它们当同一件事调优，必然得到失衡的系统。
II.

Prefill — 一次"宽矩阵"的算力时刻

Compute-bound · arithmetic intensity 高

Prefill 阶段，N 个 prompt token 同时进入 Transformer。Q/K/V 投影是一次形状为 [N, d_model] × [d_model, d_model] 的矩阵乘法——所有 token 并行算。在这种大矩阵乘里，每读一字节权重，能服务多个 token 的乘加，arithmetic intensity（FLOPs / byte）很高，于是 GPU 的 tensor core 真正吃满了。

Fig. 1Prefill 把 prompt 当成一个矩形批次：所有 token 在同一步里并行通过每一层。点击播放，看一层接一层地完成。
8 个 token × 6 层 — 演示用
为什么是 compute-bound 权重矩阵被一次读入、被很多 token 同时使用——Roofline 上的工作点落在算力线下面。瓶颈是 GPU 的 FLOPs，加大 batch 也不会救你太多。
III.

Decode — 每吐一个字，都要重读一遍历史

Memory-bound · arithmetic intensity 低

Decode 阶段每一步只生成 一个 token。这个 token 的 attention 要看到前面 N + t 个位置的 K 和 V——而这些 K/V 已经在 KV Cache 里。于是单步 decode 做的是：读一份权重（GB 级）+ 读一段 KV Cache（也是 GB 级）→ 算出一个 token。

这次的矩阵乘法形状是 [1, d_model] × [d_model, d_model]——瘦矩阵。读了那么多字节的权重，只服务一个 token 的乘加，arithmetic intensity 极低，工作点落在 Roofline 的"屋顶"以下、带宽线之上。GPU 的 tensor core 在等数据。

Fig. 2Decode 像传送带：每一格只生成一个 token，下一个 token 要等上一个写完 KV 才能开始。每一步都得把所有权重和 KV 重读一遍。
12 步 — 注意每一步都要回头读历史
为什么是 memory-bound 生成 1 个 token，需要读完整套权重 + 一份 KV Cache。"读了一大堆只算了一点"，HBM 带宽先于 FLOPs 用尽。这就是为什么 batch 起来收益巨大、为什么 KV Cache 大小直接卡住吞吐。

V.

信封背面：Llama-3-70B 的两段时间

不是 benchmark，是数量级感觉

用 Llama-3-70B 的真实形状做一遍粗算：L = 80 层，d_model = 8192，n_kv_heads = 8，head_dim = 128，FP16。假设跑在一张 H100（≈ 989 TFLOPS dense FP16，HBM 带宽 ≈ 3.35 TB/s），权重总量约 140 GB（FP16）——单卡放不下，常见做法是 8× H100 上跑 TP=8，每卡承担 ≈ 17.5 GB 权重 + 自己那一份 KV。下表用单步、单卡的简化数字给出 数量级。

量Prefill / tokenDecode / token意味着
需要读的权重 ≈ 17.5 GB（共享给 N 个 token） ≈ 17.5 GB（每步重读一次） 权重读取次数 = decode 的瓶颈
单 token KV 写入 (per layer, both K&V) 2 × 8 × 128 × 2 B = 4 KB · 80 层 → ≈ 320 KB / token 1 个对话 4k tokens ≈ 1.25 GB KV
arithmetic intensity 高（≈ N × 数百 FLOPs/byte） 低（≈ 几 FLOPs/byte） Roofline 两侧

看最后一行——Decode 的 batch 收益是几乎线性的，因为多个请求可以共享同一次"读权重"。这就是为什么 vLLM、TGI、TensorRT-LLM 都在 decode 这一侧花大力气做 continuous batching：每多塞一个请求，几乎免费。Prefill 那边多塞一个请求？算力本来就吃满，没什么便宜可占。

一个反直觉 Prefill 处理 1000 个 token 比 Decode 生成 1000 个 token 快得多。一段 1k prompt 大约 100 ms 出第一字；之后再生成 1k token 要 15–25 秒。同样多的"token 工作量"，时间差出两个数量级。

VI. 记下这几条

  1. 一次 LLM 请求是两段不同性质的计算：Prefill（compute-bound）和 Decode（memory-bound）。任何把它们当同一件事的优化决策都会偏。
  2. 用户感受到的 TTFT 由 Prefill 决定，TPOT 由 Decode 单步决定。两者的优化手段几乎不重叠。
  3. Decode 的瓶颈是"读完整套权重 + KV Cache 才生成 1 个 token"。这是 KV Cache 大小直接限制吞吐、batching 收益巨大、speculative decoding 划算的根本原因。
  4. Prefill 的瓶颈是 GPU 的 FLOPs。Chunked prefill、prefix caching、并行 prefill 都在这一侧做文章；continuous batching 在这一侧帮助有限。
  5. 下次看到一条推理优化技术，先问自己：它在压 TTFT 还是压 TPOT？落到 Roofline 的哪一侧？答案不清楚的优化，多半是在解决错误的问题。
