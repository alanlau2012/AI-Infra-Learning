KV Cache

把每一个生成过的 token 都"记"下来——是 LLM 推理能跑动的前提，也是它最先撞到内存墙的原因。

I

缓存的诞生

没有 KV cache 的 decode，是一种 O(n²) 的浪费。

自回归生成的每一步，模型都需要让当前 token 与所有历史 token做 attention：把当前 query 与历史 key 做点积，再用 softmax 加权聚合历史 value。

朴素地实现，每生成一个新 token，就要重新把过去 n 个 token 重新跑一遍 K、V 投影——第 1000 个 token 要重算 1000 次 K/V，第 2000 个要重算 2000 次。整段生成的累计计算量是 O(n²)，而其中 O(n²)−O(n) 都是冗余：那些历史 K、V 的值并不会因为后来又生成了一个 token 而改变。

KV cache 的全部点子就在这一句话里：K 和 V 算一次，就把它存住，后续只往里追加。原本平方级的累计开销，被压成线性的"读 + 加一行"。decode 阶段的 attention 由此从一个计算密集的瀑布，变成一段在显存里来回搬数据的窄管子——这也正是它会成为memory-bound的根因。

核心抽象：KV cache 是一个 append-only 的环境状态。每一步 decode 只贡献一行新的 K/V，attention 的另一侧——过去的所有 K、V——是被读出来的，不是被算出来的。
II

一个 token 到底存什么

不是 hidden state，不是 logits——是每一层 attention 的 K 和 V。

常见的误解是把 KV cache 想成"模型的隐藏状态"。它不是。每一层 transformer 内部都有自己独立的 attention，因此 KV cache 也是每层一份：一个 80 层的模型，每个 token 在缓存里其实占了 80 套 K/V。

对于一个 token，在单层里被存下的形状是：

K · shape = [n_kv_heads, head_dim]
V · shape = [n_kv_heads, head_dim]
# 数据类型一般是 fp16 / bf16 (2 字节) 或 fp8 (1 字节)

因此每个 token 在整个模型里占用的 KV 字节数为：

bytes_per_token = 2 × layers × n_kv_heads × head_dim × dtype_bytes
# 系数 2 来自 K 和 V 各一份

把所有 token、所有并行 sequence 一起算，整张卡上的 KV cache 占用就是：

KV_total = bytes_per_token × seq_len × batch_size
请记住这条线性关系。 KV cache 与 seq_len × batch 严格成正比——既不会因为 prompt 共享前缀而减少（除非你显式做 prefix sharing），也不会因为 attention 是 sparse 而便宜。它就是一块越长越胖的连续 buffer。

IV

撞墙的那一刻

线性增长 + 多并发，会把任何一张卡逼到墙角。

"线性增长"听起来温和，但只要你把推理服务真正跑起来，就会发现 KV cache 是第一个触发限制的资源——往往比模型权重还要早成为瓶颈。

真正的痛点不是任何一行——而是这些场景同时存在。线上请求的 seq_len 分布是长尾的：99% 的请求很短，1% 的请求拖着十几万 token 的尾巴，但那 1% 会瞬间吃光本来留给其他 16 路并发的预算，让 batch 被迫缩小，TPS 塌方。

这正是 vLLM 在 2023 年所做的关键观察：传统实现把每条 sequence 的 KV cache 一次性预留成最大可能长度的连续 buffer，造成大量碎片与浪费。PagedAttention 把 KV cache 切成固定大小的 block（一般 16 个 token / block），用一张block table把逻辑序列映射到物理 block——KV cache 从此可以像虚拟内存一样被精细地分配、共享与回收。

关键直觉：当一种资源会随用户行为长尾增长时，把它切块、加间接表、做按需分配——几乎总是值得的。KV cache 与操作系统页表之间的相似不是巧合。
V

通往下一道门

围绕 KV cache 长出来的那一整代优化。

一旦把 KV cache 看成 LLM 推理的中心资源，过去两年大半的推理优化就能被串成一张图：

—— 结构上，MQA / GQA / MLA 通过减少 K/V 的头数（或对其做投影压缩），直接砍掉 bytes_per_token 中的 n_kv_heads 项。

—— 数值上，KV cache quantization（FP8 / INT8 / INT4）把 dtype_bytes 砍半甚至 1/4，是 KV 显存最直接的杠杆。

—— 分配上，PagedAttention 把"为最差情况预留"换成"按页按需分配"，让多路 sequence 共用一个池子，吞吐立刻起飞。

—— 调度上，continuous batching、prefix caching 都在说同一件事：尽量让相似的 KV 共享、让不同长度的请求在同一个 step 里共存。

—— 架构上，更激进的做法（attention sink、StreamingLLM、KV eviction、cross-layer KV sharing）在追问一个更尖锐的问题：是不是所有历史 token 的 KV 都值得保留？哪些可以丢、哪些可以跨层共享？

把它放回脑中的位置：当你听到任何一项推理优化，先问一句——它在 2 × layers × n_kv_heads × head_dim × seq_len × batch × dtype 这条公式里减小了哪一项？答得出来，你就抓住了它的本质。
¶

带走这五件事

KV cache 把 decode 的注意力计算从 O(n²) 压到 O(n)，但代价是把"算"换成了"存"。

它是每层、每 token、每个 KV head都要存一份的 append-only buffer，与 hidden state 是两回事。

规模公式只有一条，背下来：2 × layers × n_kv_heads × head_dim × seq_len × batch × dtype。

在生产系统里，KV cache 通常比模型权重更早成为瓶颈，因为它会随并发和上下文长度同时膨胀。

近两年大部分 inference engine 优化（GQA、PagedAttention、KV quant、prefix cache、continuous batching）本质上都是在那条公式里做减法、或重塑它的内存分配方式。

明天的门 KV cache 既然是块"会涨的内存"，就值得有自己的一套分配器。下一课：PagedAttention——把虚拟内存的思路引进 attention，是怎么做到的，又付出了什么代价。
