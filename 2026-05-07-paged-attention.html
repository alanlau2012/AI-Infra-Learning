PagedAttention — 给 KV Cache 装上一套虚拟内存

为什么 vLLM 能比朴素实现挤出 2–4× 的吞吐？答案不在 attention kernel，而在显存 allocator。

I.碎片之罪 II.分页类比 III.块表实景 IV.前缀共享 V.信封背面
I.

朴素 KV Cache 的两宗罪

朴素的实现把每个请求的 KV cache 当成一段连续 tensor：按 max_seq_len 一次性预留显存。问题是，max_seq_len 通常设到 4K、8K，但实际请求 90% 落在 200–1000 token。预留出去的显存"压住"了 GPU，但里面真正承载 token 的只有一小段。

第二宗罪：当一个请求结束、另一个请求开始时，留下的"洞"未必能塞下新请求的 max。即便整体空闲显存够用，外部碎片也让你装不下下一个请求。这两宗罪共同把可并发数压到极低 — 在 vLLM 论文里，朴素实现的 KV 利用率往往不到 40%。

Insight朴素 KV cache 的底层假设 — 每个请求一段连续显存 — 与 LLM 推理"长度高度可变 + 批次动态变化"的现实正相反。这是 PagedAttention 之前所有花哨调度都治不好的病根。
II.

操作系统教过我们怎么办

1960 年代的操作系统遇到过同一个问题：进程的内存需求是可变的，把每个进程都塞到一段连续物理内存里，会留下大量塞不进新进程的"洞"。解法是分页 (paging) — 把物理内存切成固定大小的 page，把进程的虚拟地址通过 page table 映射到物理 page。物理上不连续，逻辑上连续。

PagedAttention 把这一招直接搬到 KV cache。把 GPU 显存切成固定大小的 KV block（典型 16 个 token）。每个 sequence 维护一张 block table，把"逻辑 token 位置"映射到"物理 block 编号"。Attention kernel 在读 K/V 时不再假设连续 — 它先查 block table，再去物理 block 里取。

FIG. 2左/上：朴素实现里 sequence 必须落在一段连续显存上；当三条 sequence 大小不一时，剩余显存装不下第四条。右/下：分页后，sequence 由若干个分散的 block 组成，第四条只要凑齐够数的空闲 block 即可入队。
Insight"逻辑连续、物理离散" — 这一行字定义了 PagedAttention 的全部价值。剩下的工程都是在保护这个不变量：block table 的查表开销要小、attention kernel 要支持非连续读、block 分配/释放要原子化。

IV.

前缀共享：免费的并行采样

分页带来一个意外但重要的红利。当一条请求需要 n=4 个 sample 并行解码（beam search、self-consistency、best-of-n）时，它们共享 system prompt + 用户 query 的前缀。朴素实现要把这段 KV 复制 4 份。分页之后，4 条 sequence 的 block table 在前缀部分指向同一组物理 block，只在分叉点之后各自申请新 block。

vLLM 用一个简单的 引用计数实现 copy-on-write：共享的 block 计数 = 分支数；当某条 branch 要写入这个 block 时，先 fork 出一个新 block，把旧内容 memcpy 过去，引用计数 − 1。一段 2K token 的 system prompt 在 n=8 采样下省下的不只是显存，还有 prefill 算力。

V.

给定 80GB 的 H100，去掉 weights ~140GB（先假设走 TP=2 切 70GB）+ activation/runtime ~5GB，留给 KV 的预算约 5GB 在单卡侧。注意：以下是"单卡 KV 预算"的对比，重点是同样预算下，分页与朴素能装多少。

策略每请求占用可并发数
朴素 (max_seq_len=4096)4096 × 320KB ≈ 1.31 GB~3
PagedAttention (avg=512)512 × 320KB ≈ 160 MB + 1 块 padding~30

同样一张卡，并发数从 3 跳到 30，吞吐近乎线性放大。再叠加前缀共享，n=4 的 best-of-n 场景里前缀部分只占 1/4，显存进一步松绑。这个 10× 量级的杠杆，是 vLLM 论文里那条"2–4× 吞吐"曲线的物理来源 — 工程实测会被 attention kernel 开销和 batch composition 拖一些，但数量级正确。

对华为生态：MindIE LLM 同样内置了 paged-KV 调度，块大小通常取得比 vLLM 的 16 更大（具体默认值以对应版本文档为准），以适配昇腾 HBM 的访存粒度。HCCL 的 collective 与 paged 调度耦合，在 TP 切分时往往需要 align 到 block 边界，这是把 vLLM 移植到 Ascend 时容易踩坑的细节。

示意场景以一台单机昇腾节点跑某 30B 级模型为例（以下数值仅为示意）：朴素 KV 实现下并发可能被压到个位数；切换到 paged 调度后并发可显著提升，瓶颈从"显存装不下"迁移到"prefill 算力打满" — 这是一个健康的瓶颈迁移，意味着 KV 这条路真的疏通了。
VI.

What to remember

  • PagedAttention 不是新 attention 算法 — 它是 KV cache 的 allocator 重设计。Attention kernel 多出一次 block_table 查表，几乎不影响 FLOPS。
  • block_size 是关键工程参数。vLLM 默认 16，MindIE 的块粒度通常更大（以版本文档为准）。太小则 block_table 开销和 kernel launch overhead 上升；太大则碎片回归朴素实现的困境。
  • 外部碎片几乎被消灭，内部碎片只剩"最后一个 block 没填满"的零头 — 平均 = block_size / 2 个 token，相对预留 max_seq_len 那种浪费可以忽略。
  • 前缀共享是分页框架的副产品，不是单独模块。Beam search、best-of-n、system prompt 复用都从同一个引用计数机制中受益。
  • 瓶颈迁移意识：分页解决显存碎片之后，下一个瓶颈通常是 prefill 算力或 MoE 路由不均。一次只解决一个瓶颈，别在显存还没疏通时去优化 attention kernel。
