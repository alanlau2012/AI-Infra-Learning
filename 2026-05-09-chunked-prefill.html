把 prefill 切碎,
才能让 decode 不失稳态

长 prompt 一进来,decode 队列里所有用户的 TPOT 都被它劫持。Chunked prefill 是把这把"刀"分成薄片,与 decode token 同批共舞——以微小的 prefill 减速换取整体延迟分布的平滑。

I.

单体 prefill 的"刀刃效应"

Decode 是一个稳态过程:每个 step 大约 25–60 ms,稳稳地往下吐 token。但只要一个新请求带着 4096 token 的 prompt 进来,GPU/NPU 就被它独占——一个 step 可能跑上 1–3 秒。在这段时间里,所有正在 decode 的用户的下一个 token 都被卡住。这就是"prefill 刀刃":TTFT 看似分配给了新请求,代价却由整个 batch 的 TPOT 一起买单。

下面这张图是一个 in-flight batch 的时间线:四个老用户在稳态 decode,第 8 帧来了一位带长 prompt 的新用户。点击播放,看 decode 是怎么被"刀"住的。

Fig. 1横轴是 batch step,蓝色格子是 decode token,红色长格子是单体 prefill。Prefill 跨越了 8 个 step 的时长,期间 R1–R4 全部停摆——TPOT 在那一段从 ~30 ms 跳到 ~600 ms。
核心症状:不是 prefill 本身慢,是它"非抢占地"独占了一个 batch step,把同 batch 的 decode 一并冻结。这是 throughput 与 latency 直接冲突的经典场景。
II.

切片:把一刀分成 N 片

解决思路看起来很朴素:既然 4096 个 prompt token 一次跑完会卡 1.5 秒,那就拆成 8 段,每段 512 token,各跑 ~190 ms。但 prefill 计算本质是 attention——后面的 token 必须能看到前面所有 token 的 K/V。所以"切片"必须保证因果性:第 k 片在 forward 时,K/V 来自前面所有片 + 当前片自己。

实现层面,这正是 KV Cache 的天然能力——prefill 第 1 片写入前 512 个 K/V,第 2 片写入 512–1024,attention 时 query 长度 = 512,key/value 长度 = 已写入总长。计算量相对单体 prefill 几乎不增加(softmax 还是那个 softmax),代价是 kernel launch 多了 N 倍,以及每片的 attention K/V 长度递增。

Fig. 2把同一个 4096-token prefill 切成 1 / 2 / 4 / 8 片。总耗时只略增(kernel overhead),但每片的"档期"短了——这就是后面让它和 decode 共舞的前提。

关键观察:切片本身不省时间,甚至略亏(kernel overhead)。它真正的价值,在于把"一根长棒"变成"一串小石头"——下一节才能把石头塞进 decode 的缝里。
III.

同批混跑:prefill ⊕ decode

Continuous batching(我们 4 月 28 日那期讲过)的核心是 step 粒度的请求增减。Chunked prefill 在它之上再加一条规则:每个 step 的 token budget 是固定的(比如 2048),先尽量塞满 decode 用户(每人 1 token),剩下的 budget 用来跑 prefill 的一个 chunk。

这样一个 batch step 的输入张量会同时包含两类 token:M 个 decode token(query 长度 = 1)+ K 个 prefill token(query 长度 = K),总长度 ≤ token budget。Attention kernel 通过 cu_seqlens + causal mask 区分两者,FlashAttention v2 起对这种 variable-length packed batch 是原生支持的。

Fig. 3同一段 14 个 batch step。蓝= decode token(R1–R4),红= prefill chunk(R5,长 prompt)。切换标签看两种调度下,R1–R4 在那段时间里到底吐没吐 token。
本质:Chunked prefill 不是优化 prefill,而是把 prefill 从"独占模式"降级为"共享模式"。R5 的 TTFT 微微变长(多了几次 kernel launch),换 R1–R4 的 TPOT 不掉队。
IV.

Chunk size 这个旋钮

调小 chunk(比如 256):decode 几乎完全不掉拍,TPOT P99 漂亮,但 prefill TTFT 会被拉长——因为每个 chunk 只能用 batch budget 的一小部分,prefill 进度慢。

调大 chunk(比如 4096):退化回单体 prefill,TTFT 短了,但 R1–R4 的 TPOT spike 又回来了,P99 难看。

所以这是一道延迟分布的"裁切题"。下面用 Llama-3-70B 在单卡 A2 量级算力的近似数字算给你看——拖动滑块感受这个 trade-off。

Chunk size 是每步 prefill 的 token 预算,通常在数百到数千 token 之间权衡。具体默认值随框架与版本而变(如 vLLM 通过 max_num_batched_tokens 控制,不同版本默认值不同),应以你部署的版本实测为准。如果你的请求是几十路并发短 prompt,chunk 还可以更小;如果是低并发长上下文 RAG,chunk 要适度放大。
V.

当它失效:与 PD 分离的边界

Chunked prefill 的隐含假设是:prefill 和 decode 共用同一组权重和同一台设备。当 prompt 极长(>32K)且并发又高时,即便是细切的 prefill chunk,也会反复挤占 decode 的 attention bandwidth(KV cache 越长,decode 单步本身就越慢)——chunk 切到再细,也救不了 decode 已经 memory-bound 到极致的情况。

这正是 2024–2025 年 DistServe / Mooncake / SGLang 等系统转向 Disaggregated Prefill–Decode (PD 分离) 的动机:把 prefill 和 decode 放到两组不同硬件上,中间用 KV transfer 链路把 cache 搬过去。Chunked prefill 是单机内部的"刀工",PD 分离是把厨房一分为二——前者解决调度,后者解决资源隔离。

对我们来说,最现实的次序是:先把 chunked prefill 调到位(vLLM/MindIE 都已默认开启),把 P99 TPOT 拉回 SLO;再观察长上下文 workload 的占比是否到了需要 PD 分离的临界——这通常出现在 32K+ 上下文 + 多模态前缀缓存场景。

承前启后:Chunked prefill 用时间维度把 prefill 的尖峰摊平;PD 分离用空间维度把它彻底搬走。我们下一期会拆 PD 分离的 KV transfer 链路。
¶

What to remember

问题单体 prefill 在 batch step 内"独占且不可抢占"——这是 TPOT 长尾的最大单一来源,而不是 prefill 本身慢。

方法把一次 prefill 切成 N 片,每片当作一段普通 forward,新增的只是 kernel launch overhead 与递增的 attention K 长度;因果性由 KV cache 自然保证。

调度每个 step 的 token budget 先满足在线 decode(每人 1 token),剩下的塞 prefill chunk;FlashAttention v2 的 packed/varlen 接口让两类 token 可以同 kernel 跑完。

调参Chunk size 是 TTFT 与 TPOT 之间的旋钮:小 chunk 保 TPOT,大 chunk 保 TTFT。常见工作点在数百到数千 token 量级,具体默认值随框架版本而变,需按 SLO 实测选取。

边界当上下文极长 + 高并发把 decode 自身打成 memory-bound 时,chunked prefill 失效;这是 PD 分离登场的信号。
